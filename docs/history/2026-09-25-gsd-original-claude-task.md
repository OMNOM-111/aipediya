# AIpediya — Global Search & Discovery 1.0
## Единый мандат Claude на полную Local-реализацию

**Название версии для timeline:** «Глобальная поисковая доступность».
**Release ID:** `GSD-1.0`.
**Краткое описание:** «Подготовка AIpediya к обнаружению моделей, инструментов и полезных подборок в международных поисковых системах и AI-поиске на 22 языках».
**Среда исполнения:** Local. **Production:** только read-only аудит.

`GSD-1.0` — идентификатор этого этапа, а не выдуманная замена существующей версии приложения. Номер приложения определить по реальному репозиторию и его соглашениям.

## Мандат и ожидаемый результат

Это задача на работающую реализацию всего этапа, а не на составление плана, один аудит или демонстрационный прототип. Пройди самостоятельно: аудит → выбор архитектуры → реализация → автоматические проверки → браузерный/crawler QA → исправления → итоговая Local-приёмка.

Цель текущей сессии — закончить весь доступный Local scope. Не останавливайся после плана, архитектурного решения, одного модуля или условных 90%. Внешний блокер конкретной интеграции фиксируй и продолжай независимые пункты. Не обещай обход лимита сервиса: при реальном исчерпании сохрани проверяемое состояние и точную точку продолжения без повторного исследования.

Этот мандат заменяет прежнее предложение «Task 1: только аудит, затем STOP перед выбором URL». Инженерный выбор URL-архитектуры и её реализация в Local делегированы тебе. Отдельное разрешение на каждый внутренний шаг не нужно. Это НЕ разрешение на Production, внешние отправки, новые расходы или изменение редакционных решений каталога.

Результат — международная техническая поисковая инфраструктура. Первое место, фактическая индексация и цитирование сторонними системами не являются результатами, которые можно объявить достигнутыми по Local-тестам.

### Неприкосновенные ограничения

- Продолжать Django SSR и существующий catalog + right-panel UX. Models и Tools раздельны. Сохранить темы, RTL, language switcher, клики, скролл, сортировки и функциональность предыдущих доработок. Не делать редизайн или новый frontend-стек.
- Сохранить pk/slug, текущие номера, публикационное состояние, цены, оценки, источники, переводы и историю. Не разрешать спор нумерации в рамках SEO. Для идентичности использовать Record ID/slug, не номер строки или текущий хронологический номер.
- Не выполнять full translation backfill, массовый ремонт переводов или Azure-вызовы. Существующие 22 локали, ContentTranslation, automatic future pipeline и token protection сохранить. Чтение страницы, sitemap или dataset никогда не должно запускать перевод.
- Deferred eval-gap сохранить отдельным пунктом: `412,820 billable chars; previously recorded F0 shortfall: 108,605`. Это исторически записанный остаток, не live-проверка квоты. Не закрывать его шаблонным обходом и не выдавать за переведённый.
- Не публиковать master XLSX, research records, внутренние заметки, private editorial history, секреты или скрытых кандидатов. Не копировать Local SQLite в Production.
- Не менять StratForge, общие сервисы, туннели, DNS/WAF или серверное состояние. Существующий shared-server SSH допустим только для read-only проверки AIpediya внутри `/srv/aipedia` и её службы, без просмотра/вывода секретов.
- Не выполнять deploy, rollback, push, release tag, массовую отправку URL или account/DNS actions. Старое разрешение на другой выпуск не распространяется на GSD-1.0. Выпуск этой версии — только после отдельного утверждения итогового scope по актуальному `docs/RELEASE.md`.

### GSD-02 — Окончательная архитектура языковых URL

Сравни на реальном проекте A: indexable `?lang=` и B: locale paths. Учти canonical/hreflang, исходящие и входящие ссылки, текущие известные индексированные URL, SEO-hubs, CDN/cache, переключение языка, redirects и стоимость сопровождения. Отсутствие доступа к Search Console не выдавай за отсутствие входящих ссылок. Используй актуальные официальные источники; не объясняй преимущество пути выдуманным гарантированным приростом ранжирования.

Самостоятельно выбери один вариант, запиши ADR и реализуй его в Local. В записи отдели делегированное инженерное решение от ещё не выданного разрешения на Production; не утверждай, что владелец отдельно согласовал выбранный вариант. При переходе на paths определи English root versus `/en/`, совместимость старых ссылок, нормализацию locale codes и trailing slash. Старые рабочие языковые ссылки должны иметь однозначный 301 на эквивалентную страницу без цепочек и циклов; полезные UX-параметры сохраняются по явным правилам. Не редиректить неизвестные или скрытые сущности на главную.

Централизуй построение URL. Язык явного localized URL не должен меняться из-за cookie, геолокации или User-Agent. Не делать постоянные языковые redirects на основе IP. Для default/x-default определи устойчивое поведение; ручной выбор языка сохраняй без кэширования персонального языка как общего ответа. Переводы и их ключи не мигрировать.

**Приёмка:** решение принято и реализовано; старые ссылки, canonical URL builder, language switcher, direct entity links и browser history проходят тесты.

### GSD-03 — SSR-карточки и правила индексируемости

Direct Model/Tool URL без JavaScript должен возвращать содержимое конкретной сущности, а не только общий каталог. Сохрани панель как интерфейс; значимые сведения присутствуют в исходном HTML и доступны человеку, включая сведения из вкладок. Никакого отдельного скрытого SEO-текста или иной версии фактов для роботов.

Показывай имеющиеся применимые сведения: точное имя, разработчик, локализованное описание и назначение, возможности/ограничения, страны, release date и её точность, статус, цены с валютой/единицами/условиями, API/web/local access, контекст и модальности моделей, лицензирование/open-weight, независимые проверки, источники и даты проверки. Tool не получает неприменимые model-only поля. Неизвестное остаётся неизвестным; дата проверки не подменяет выпуск; собственный рейтинг не рассчитывать.

Сделай единую политику публичности и SEO-readiness для views, sitemap, hreflang, hubs, datasets и notifications. Учитывай подтверждённое публикационное состояние и master decisions через проверенный снимок/существующий контракт, не читая XLSX на каждом production GET. NEEDS_REVIEW, редакционно скрытые записи и связанные внутренние сведения не должны попадать ни в один публичный канал. Не повышай статус записи автоматически ради SEO.

Для каждой entity×locale вычисляй результат с причиной: indexable, not-ready/noindex, not-public. Проверяй актуальность основного локализованного текста, а не только интерфейс. Бренды/ID/URL/числа не считать английским fallback; отсутствующее исходное поле не считать отсутствующим переводом. Непереведённый второстепенный eval-gap не должен автоматически блокировать всю страницу с полноценным локализованным основным содержимым; правило и реальные исключения документируй.

**Приёмка:** полный реестр readiness; 0 утечек скрытых записей; SSR Models/Tools и причины исключений доказаны. Количество переводов не выдать за количество индексируемых URL.

### GSD-04 — Международные SEO-сигналы и sitemap

Для SEO-ready страниц реализуй локализованные title/meta description, предметный H1, self-canonical, взаимные hreflang с self-reference, x-default, корректные html lang/dir. English как исходный язык не означает canonical всех переводов на English. Набор alternates включает только допустимые canonical 200-страницы; noindex/404/redirect targets в него не включать.

HTML hreflang должен работать самостоятельно, без зависимости только от sitemap. Sitemap index и дочерние sitemap формируй из того же readiness-реестра, разделяя типы/локали/пакеты по необходимости. Проверяй лимиты числа URL и несжатого XML, XML escaping, отсутствие дублей/скрытых записей/localhost, реальные lastmod. Не обновляй lastmod на каждом просмотре. Отдельно считай `<loc>` и alternate links.

Local остаётся loopback и защищён от индексации. Production-mode SEO проверяй в изолированных тестах, не отключая защиту Local глобально. Исключи произвольный Host из построения canonical, внешние redirects при Local-навигации и языковое смешение кэша.

**Приёмка:** полный HTML/sitemap consistency audit, все 22 локали учтены, количество indexable URL совпадает с readiness-реестром.

### GSD-05 — Фильтры, пагинация и обход

Инвентаризируй q, sort, price, category, country, status, access, platform, page, partial, panel-state и другие параметры. Сохрани UX, но исключи бесконечные индексируемые комбинации. Политика robots/noindex/canonical должна быть согласованной: robots-блокировка не заменяет удаление из индекса, а недоступный роботу noindex не является рабочим механизмом исключения.

Пагинацию разбирай отдельно от произвольных фильтров. Полноценные страницы последовательности должны иметь конечный диапазон, обычные `<a href>` и собственный canonical; не склеивай page=2 и далее с первой страницей. Сохрани доступность всех публичных entities без infinite-scroll JS. Невозможные номера страниц возвращают корректный статус. Partial endpoints не являются SEO-страницами.

Canonicalize только действительно эквивалентные варианты; не объявляй любую уникальную фильтрованную выборку копией корня. Произвольный поиск/сортировки не превращай в отдельные landing pages. Не запрещай все query URLs правилом, которое заодно убивает `lang` или рабочую пагинацию.

**Приёмка:** конечная карта обхода, проверенные параметры/редиректы, отсутствие crawl traps и доступность сущностей без JS.

### GSD-06 — Методология и structured data

Сделай доступную из существующего интерфейса публичную локализованную Methodology page. Объясни действующие правила источников, подтверждения существования и публикации, точных/приблизительных дат, цен и единиц, происхождения, независимых оценок, неизвестных значений, конфликтов и обновлений. Отличай реализованный процесс от будущих планов. Не обещай ежедневную проверку или собственный рейтинг, если этого нет.

Новые короткие тексты и metadata локализуй через существующую систему, повторно используя её словарь. Не запускай перевод существующего каталога. Некачественные/отсутствующие новые локализации явно отмечай; английский fallback не выдавай за готовую переводную страницу.

Добавь семантически корректный JSON-LD: Organization, BreadcrumbList где уместно, Dataset/DataCatalog/DataDownload на реальных dataset-страницах. Иные типы — только при соответствии содержимому. Никаких выдуманных AggregateRating/Review, лицензий, цен или адресов компании. Structured data должна соответствовать видимому контенту; безопасно экранируй её.

**Приёмка:** маршрут, навигация, локализации, SEO-сигналы и schema validation; методология описывает реальные правила, без фиктивных фактов.

### GSD-08 — Search discovery, AI-crawlers и IndexNow

Проверь официальные актуальные требования Google Search Console, Bing Webmaster, Yandex Webmaster, Baidu Search Resource Platform, Naver Search Advisor, Seznam/IndexNow, Brave и релевантных AI-search providers. Для каждого запиши: способ обнаружения/подтверждения, техническая готовность, наличие live-access, что проверено и какое минимальное действие владельца осталось. Не придумывай универсальную регистрацию, поддержку API или доступность одинакового способа verification во всех странах.

Аудит crawler-access должен разделять обычный HTTP, spoofed User-Agent и подтверждённый реальный обход. Проверяй Googlebot/Bingbot/YandexBot, OAI-SearchBot, PerplexityBot, Claude-SearchBot и другие подтверждённые официальными документами агенты. Search crawlers, training crawlers и user-triggered fetchers — разные категории. Существующие решения о training access не отменяй. Не ослабляй WAF по одному UA и не отключай защиту глобально. Cloudflare-изменения только подготовь как точечный release scope.

Проверь существующий IndexNow и доведи до event-driven механизма: создание, существенное обновление, снятие публикации/удаление публичного URL → персистентная запись изменения → отправка после доступности соответствующего Production-состояния. Используй простой журнал/outbox и management command, без отдельного брокера/Redis. Нужны dedup, идемпотентность, bounded retries, корректная обработка 200/202/4xx/429/5xx, batch limit и host allowlist. События удаления сохраняют ранее публичный URL; их нельзя потерять фильтром «теперь не indexable».

Изменение перевода уведомляет только затронутые locale URLs; обычный запуск/GET не отправляет весь каталог. Все реальные отправки, scheduler и initial submission в Local выключены; протестируй mock/dry-run. Принятие URL сервисом не означает индексацию.

**Приёмка:** работающий Local notification pipeline, проверенная crawler/discovery matrix и точный activation checklist. Login/DNS/Production actions остаются отдельными внешними зависимостями.

### GSD-09 — SEO-hubs и основа авторитетных материалов

Реализуй небольшой реестр заранее разрешённых intent-based hubs, а не генератор всех фильтров. В scope до 10 конкретных полезных подборок из следующих направлений: модели для программирования, музыки, видео; бесплатный доступ; API; open-weight; выбранная страна; выбранный год; большой контекст; инструменты программирования.

Каждая подборка: стабильный URL, детерминированная выборка опубликованных записей, понятный критерий включения, локализованный краткий текст, полезные результаты, metadata, canonical/hreflang/sitemap, обычные внутренние ссылки и существующий catalog/panel UX. Free tier не приравнивай к бесплатному API, open-weight — к open-source, а большой контекст — к лучшему качеству.

Пустые, неподтверждённые и не дающие самостоятельной пользы подборки не индексируй. Не создавай сотни country/year URL за счёт слова «10 hubs». Отчитайся отдельно о реализованном механизме, готовых hubs и ещё неготовых кандидатах.

Подготовь повторно используемые, проверяемые агрегаты по опубликованным данным для будущих статистик/отчётов; обозначь границы будущих histories/API/ratings, не имитируя отсутствующую историю. Поддержи sharing metadata существующими brand assets. Массовый контент-маркетинг, рассылки, соцсети и покупка backlinks вне этого релиза.

**Приёмка:** конечный реестр hubs и доказанная польза/фактичность каждого опубликованного варианта; нет thin-content генерации.

### GSD-10 — Мониторинг, QA и завершение

Сделай повторяемый технический отчёт и точки подключения доступных источников данных: indexable/discovered/crawled/indexed URL, sitemap/canonical/hreflang ошибки, impressions/clicks/query/country/locale, AI referrals/citations там, где есть подтверждённые данные. Разделяй собственный crawler, server logs и сведения search provider. Locale из URL не является доказательством страны посетителя; referrer не доказывает все AI-цитирования. Нет доступа/данных — null/not connected, не выдуманный 0 или график из mock.

Мониторинг не должен зависеть от нового крупного dashboard: используй существующие интерфейсы, команды и машиночитаемые отчёты. Подготовь integrations/schedule к последующему включению без фоновых отправок из Local. Секреты, персональные поисковые строки и избыточные user data не должны утекать в публичные отчёты.

Проведи полный текущий regression suite, migration/check/diff checks, все 22 локали в систематическом rendered-аудите, readiness/sitemap graph checks и реальные браузерные сценарии. Минимальная визуальная выборка: EN/RU/UK, одна европейская латинская локаль, CJK и обе RTL; desktop/mobile, обе темы, Models/Tools, direct links, panel, Escape/close, language switch, filters, pagination и back/forward. Production внешне проверять ограниченной выборкой, не полным агрессивным crawl.

Проверяй сохранность данных/переводов/публикационного состояния относительно baseline, отсутствие секретов, CSV/JSON-LD безопасность и отключение реальных сетевых записей в Local. Не ослабляй тесты ради PASS. Предсуществующие ошибки и новые регрессии различай; непроверенное не называй пройденным.

Обнови документацию и собери AI_CONTEXT штатным packer. Подготовь точный release scope с dependencies, миграциями, redirect map, sitemap counts, deployment/rollback условиями и действиями активации. Артефакт из старого HEAD без незакоммиченных изменений не является текущим Local-кандидатом. Сопоставь кандидат с проверенным working tree и актуальной процедурой выпуска; не публикуй и не подменяй порядок выпуска самостоятельно.

**Приёмка:** фактический Local handoff с воспроизводимыми тестами и evidence; внешний launch ещё не объявлен выполненным.

## Организация работы и экономия контекста

Основную реализацию веди одним координатором. При реальной пользе используй до двух параллельных субагентов с непересекающимися файлами и узкими задачами; общий DB/XLSX, routing и номера миграций не редактировать конкурентно. Субагент возвращает вывод, файлы и проверки, а не полный журнал. Нет субагентов — продолжай последовательно.

Основной effort Medium. Не включай Extra/Max автоматически на весь этап и не меняй настройки аккаунта. Для сложного найденного дефекта допустима отдельная усиленная проверка при доступной настройке; фактический режим не выдумывать. Повторно используй собранные source facts, URL builder, readiness registry и audit tooling. После связанной группы правок запускай targeted tests, а полный suite — в интеграционных точках. Не создавай десять параллельных систем документации и не трать сессию на косметику вне scope.

Веди один основной статус в `docs/EXECUTION_STATE.md`, решения в `docs/DECISIONS.md`, поисковый контракт в `docs/SEARCH_DISCOVERY.md`; evidence — в `artifacts/global-search-discovery/GSD-1.0/`. Машиночитаемый progress/timeline record должен ссылаться на эти источники, а не противоречить им.

## Как считать и показывать прогресс

Не используй субъективное «почти 90%». Для каждого GSD-пункта храни число критериев, implemented count и verified count. `Verified %` пункта = пройденные критерии / все зафиксированные Local-критерии пункта × 100. Общий Local acceptance = сумма verified % пунктов с весами из плана. Это доля критериев приёмки, не оценка затраченного времени.

Раздельно показывай:
- Implementation coverage — сколько предусмотренного реализовано.
- Local acceptance — сколько критериев реально проверено.
- External activation — по каждой системе отдельно: prepared / owner action / submitted / live-verified.
- Data quality — отдельная существующая очередь, не процент готовности SEO.

Непроверенная реализация не считается VERIFIED. Внешний login blocker не останавливает код, но не становится «интеграция подключена». Local 100% не означает 100% worldwide launch. Не удаляй сложные критерии из плана и не объявляй отсутствие translations или реального browser QA несущественными без объяснения.

После законченного блока давай короткий отчёт: версия; implementation/verified; что готово; что осталось; блокер; следующий пункт. Не спрашивай каждый раз «продолжать?».

## Обязательный финальный отчёт и остановка

Верни таблицу всех десяти GSD-ID: название, статус, implemented %, verified %, фактический результат, evidence, конкретный остаток. Затем укажи:

1. Local/GitHub/Production baseline и финальные состояния; существующие и новые изменения раздельно.
2. Выбранную URL-архитектуру, примеры старых/новых адресов и результаты redirects/SSR/metadata/hreflang/sitemap/facets.
3. Публичные entity counts; потенциальные entity×locale URLs; реально indexable, excluded и not-ready с причинами.
4. Methodology/schema, оба dataset, hubs и notification/monitoring результаты.
5. Числа тестов PASS/FAIL/SKIP, rendered/browser coverage, сохранность данных и оставшиеся дефекты.
6. Единый список минимальных owner actions по внешним системам; ничего не называть подключённым без evidence.
7. Точный scope публикации этой версии и release dependencies; Production и внешние отправки не выполнены.

**После завершения доступного Local scope и QA остановись перед Production. Не завершай работу раньше лишь потому, что выполнен аудит, написан план или достигнута круглая цифра прогресса.**

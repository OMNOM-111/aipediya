`release_sequence` — неизменяемый номер выпуска, `app_version` — SemVer.
До 1.0 новый пользовательский пакет увеличивает minor (`v0.12.0`), исправление
опубликованного пакета — patch (`v0.12.1`). `v1.0.0` требует отдельного
решения владельца. Отменённый номер остаётся в карточке с `cancelled` или
`superseded` и причиной; следующий пакет получает следующий номер.

Одна карточка проходит `in_progress` → `review` (Local QA) → одобрение
владельца → `done` после Production QA. `current_local` и
`current_production` независимо указывают на существующие карточки.
До owner review собирается автономный `timeline.html`; build gate проверяет
его отпечаток и фактический состав изменений, Local QA, approval и версию
архива. После deploy и публичной проверки
`tools/finalize_release_history.py` обновляет ту же карточку, указатель
Production и автономный HTML. Исторические Local-only задачи сохраняются
в ленте, но не занимают Release #.

`docs/timeline.json` — единый реестр этапов сайта и текущего пакета. Раздел
`entries` хранит паспорт GSD-1.0 и критерии; `product_history` содержит только
проверенные в документах публичные этапы и короткие подписи для Local-страницы.
История сайта не связана с `Public Number` моделей и инструментов.

Страница `/history/` видна только в Local. В Production маршрут отвечает 404:
в проекте пока нет отдельного входа владельца, а открытый пакет содержит
внутренние замечания. Доступные на странице документы выдаются только в Local
из фиксированного списка `catalog/product_history.py`; закрытые artifacts,
секреты и локальные абсолютные пути не выдаются. Для публикации истории нужен
отдельный проект авторизации и явное решение владельца.

Автономный просмотр — `timeline.html` в корне рабочего проекта. Он собирается из
`docs/timeline.json`, текущего контекста и allowlist документов истории через
`tools/build_product_history.py`; штатный сборщик `tools/pack_ai_context.py`
обновляет HTML перед созданием AI_CONTEXT. При открытии пользователем ничего не
собирается. CSS, JavaScript, изображения, история и тексты источников встроены в
один файл; сетевые зависимости отключены CSP.

После выпуска #015 внутренний маршрут `/ru/history/` в Local отдаёт этот же
собранный автономный документ, сверяя его SHA-256 с `docs/timeline.json`;
при устаревшем снимке отвечает 503 до штатной сборки, не меняя файлы при
открытии. Для английского маршрута меняется лишь начальная редакция RU/EN.
Local-only CSP разрешает встроенные CSS/JS при запрете сетевых соединений;
Production по-прежнему отвечает 404. На горизонтальной ленте видны только
пронумерованные Release #001–#022, все по порядку; #018–#022 закрыты с
Local ✓, Owner ✓ и Production ✓; #022 закрыт так же.

В ленте готовность этапа (`progress`: `done` / `in_progress` / `planned`)
отделена от публикации (`open` и окружение). Синий кружок с галочкой означает
выполненную работу, в том числе автономную историю, завершённую только в Local;
жёлтый с многоточием — работу в процессе; жёлтый пунктирный — план; жёлтое кольцо
с «!» (`progress: review`) — работа реализована и проверена исполнителем в Local,
но ждёт визуальной приёмки владельца. В `done` карточку переводят только после
утверждения владельцем (решение `D-2026-09-26-timeline-owner-review-state`).

проекта, а не командой агенту начать работу. Исполнитель работает только по

## Порядок сопровождения

**Definition of Done:** обязательное закрытие каждой самостоятельной задачи
определено в корневом `AGENTS.md`. До отметки `done` исполнитель проверяет Local,
классифицирует остаточные расхождения, разбирает каждый dirty/untracked файл,
фиксирует и отправляет нужные изменения в GitHub, выполняет разрешённый выпуск
с Public QA, записывает независимые состояния Local/GitHub/Production и собирает
автономную историю и AI_CONTEXT. Неизвестные пользовательские файлы не удаляются;
намеренные master-only данные и реальные follow-up задачи называются явно.

1. Перед новой задачей прочитать открытый пакет `docs/timeline.json`, незакрытые
   замечания в `docs/EXECUTION_STATE.md`, решения и отчёты выпусков. История
   должна включать самостоятельную задачу, а не объединять разные работы одной
   строкой только по причине общего будущего выпуска.
2. После значимого изменения состояния обновить соответствующую задачу и
   критерии в `docs/timeline.json`; указать проверяемое evidence, отдельно
   техническую проверку Local, решение владельца и Production. Не выводить
   личное одобрение из тестов или commit. Отдельно отразить, что сохранено
   в Git, что работает в Local и что проверено публично. Номера этапов сайта
   не связаны с `Public Number` каталога. Не менять запись при каждом мелком
   редактировании.
3. Одновременно обновить `docs/EXECUTION_STATE.md`; новые решения оформить в
   `docs/DECISIONS.md`, завершённый выпуск — в `docs/history/` и `docs/RELEASE.md`.
   Статус должен назвать изменённое, незавершённое и следующий шаг.
4. До закрытия этапа выполнить Local QA и собрать AI_CONTEXT установленным
   `tools/pack_ai_context.py`. Сборщик формирует `timeline.html` из источников
   перед упаковкой; просмотр владельцем готового HTML ничего не собирает.
   Пакет AI_CONTEXT — сборка, не второй статус.
5. Production отмечать опубликованным только по подтверждённому выпуску и
   публичной проверке. Текущий онлайн-статус отдельно проверять перед заявлением
   о нём; commit, push и кнопка Production доказательством не служат.

Исторические пробелы оставлять неподтверждёнными. Старые отчёты не переписывать
для подгонки под текущий экран.
